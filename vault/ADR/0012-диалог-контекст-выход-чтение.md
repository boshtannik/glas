# ADR-0012: Диалог — контекст и ссылки, выход в новый навык, чтение в навыке

**Статус:** принято · **Дата:** 2026-10-16
**Связано:** [[ADR-0011-сессия-и-подтверждение]], [[Контекст-и-память]], [[Навыки]], [[Промпты]], [[Флоу-UI]]

## Контекст

Ментальный UX-тест вскрыл вопросы, которых не было в [[ADR-0011-сессия-и-подтверждение]]:

1. Пользователь ставит таймер, всё подтверждает, таймер **успешно поставлен**, сессия
   **закрылась**. Сразу жмёт и говорит «**а теперь удали**» — как модель узнаёт, *что* удалять?
2. Как **не застрять**, если в ответ на висящий вопрос (подтверждение/уточнение) пользователь
   говорит совсем другое?
3. «Удали будильник», а их **три** — как выбирать?
4. Что делает **повторное нажатие PTT** во время обработки/озвучки?

Ответы Jack (2026-10-16): ссылки — из контекста; не-ответ → **выход в новый навык**; список
ассистент **читает сам**; чтение — это **дополнительный метод в каждом навыке** (не отдельная
сущность); повторное нажатие PTT — **перебивание**.

## Решение

1. **Сессия и контекст — разные вещи.**
   - **Сессия** — короткая: пока не завершён многошаговый ход (ждём подтверждение/уточнение).
   - **Контекст (скользящее окно)** — длинный: последние ходы; **закрытие сессии его не стирает**.
     Именно окно разрешает ссылки «его/это/теперь/ещё раз». См. [[Контекст-и-память]].

2. **Ссылки разрешаются через контекст (скользящее окно).**
   - В окно пишется компактная строка результата с параметрами:
     `A: set_timer {duration_seconds:300} → ok, id=timer#1`.
   - **`id` результата — не отдельная сущность и не «память объектов»**: это просто **текст в строке
     контекста**. Навык при исполнении кладёт в результат `id`, который вернула ОС (напр. cookie
     `timed`), а ядро печатает его рядом: `→ ok, id=…`. Значение `id` — то, что дала ОС; формат в
     примерах иллюстративен. Никакого трекера/реестра объектов нет.
   - «удали его», «удали это», «повтори», «ещё раз» резолвятся моделью по контексту; если `id` в
     строке есть — ссылка точная, иначе модель опирается на текст хода и/или `read`.

3. **Выход в новый навык (exit).**
   - В ожидании ответа реплика, которая **не является ответом**, **не залипает** и не переспрашивает:
     сессия **выходит**, реплика заново резолвится как **новый ход**.
   - Навык найден и **включён** → исполняем; **нет/выключен** → обычный флоу: «такого навыка нет /
     он выключен» (см. [[ADR-0011-сессия-и-подтверждение]]).
   - **Безопасность сохраняется**: не-ответ **не** трактуется как «да» на опасный вопрос.

4. **Перебивание = повторное удержание PTT.**
   - Во время `Thinking`/`Speaking` нажатие PTT **прерывает** текущее (глушим TTS/инференс) и
     начинает новую запись. Это то, что Jack называл «отменой голосом».
   - **Никакого всегда-открытого микрофона**; эхо не мешает (ассистент молчит до начала записи).

5. **Чтение — дополнительный метод навыка (не отдельная сущность).**
   - У навыка, помимо `execute` (действие), может быть **`read`** (запрос, опционально):
     - `BuiltinSkill` — Rust-метод,
     - `DeclarativeSkill` — декларативный `read` (dbus-запрос) в манифесте.
   - `read` возвращает **данные** (список/значение) для ответа или **конкретизации** уточняющего
     вопроса. Пример: «удали будильник» → `read` отдаёт `[07:00, 08:00, 09:00]` → ассистент:
     «У тебя 3 будильника: 7:00, 8:00, 9:00. Какой удалить?».

6. **Уточнение (slot-filling) использует `read`, когда это улучшает вопрос.**
   - Модель задаёт уточняющий вопрос; если навык умеет читать кандидатов — вопрос **конкретный**
     (со списком), иначе общий. См. [[Навыки#Дозапрос данных (slot-filling)]].

7. **Ответ на уточнение продолжает тот же навык (держим контекст).**
   - Пока навык ждёт недостающий параметр, его `id` и **уже собранные `params`** хранятся в сессии.
   - Реплика-ответ трактуется как **продолжение этого навыка**:
     - модель вернула **тот же** навык → её параметры **сливаются** с уже собранными;
     - модель вернула **`unknown`** (не разобрала короткий ответ «на 8») → сырой текст подставляется
       прямо в **недостающий параметр** (с приведением к объявленному типу);
     - модель вернула **другой** навык → **выход** в новый навык (п. 3).
   - Так короткие ответы («на 8», «второй», «10 минут») работают даже со слабой моделью, а смена
     намерения не залипает. Реализовано в `glas-core` (`dialog.rs`: `run_clarified`).

### Обновлённый трейт `Skill`

```rust
trait Skill {
    fn manifest(&self) -> &Manifest;
    fn validate(&self, params: &Params) -> Result<(), SkillError>;   // дефолт — из манифеста
    fn execute(&self, params: &Params, ctx: &Ctx) -> Result<Outcome, SkillError>; // действие
    fn read(&self, params: &Params, ctx: &Ctx) -> Result<Data, SkillError>;       // опц.: запрос
}
```

`Outcome` — результат исполнения (краткое резюме + опционально **`id` от ОС**); это то, что
попадает в строку контекста «last action».

## Почему так

- Ссылки в диалоге («удали его») — типичный кейс; окно (+ `id` в строке, если ОС его дала) решает
  его надёжно даже для маленькой модели.
- «Выход» убирает залипание в ожидании, сохраняя безопасность сужения.
- Перебивание нажатием PTT не требует always-on микрофона и echo cancellation.
- `read` как метод навыка даёт конкретные уточняющие вопросы без новой сущности в архитектуре.

## Последствия

+ Диалог предсказуем: не залипает, понимает ссылки, даёт конкретные уточнения.
+ Перебивание дёшево и приватно.
− Нужно писать результат хода (и `id`, если ОС его дала) в строку контекста.
− У навыка появляется второй (опциональный) путь — `read`; нужен и для builtin, и для декларативного.
− Нужны правила: что считать «ответом», что «выходом»; как долго `id` результата живёт в окне.

## Открытые вопросы

- Как долго `id` результата доступен (пока в окне)? Отдельный «последний объект» не держим.
- «Повтори»/«ещё раз» — отдельный интент или резолв из контекста?
- Формат `Data` для выбора из списка (`options`), нумерация/время как ключи выбора.
- Декларативный `read`: как описывать выборку/фильтр данными.
- Ограничение числа «выходов» (защита от циклов), если пользователь тасует навыки?
