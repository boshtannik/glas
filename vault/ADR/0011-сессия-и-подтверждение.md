# ADR-0011: Диалоговая сессия, сужение ввода при подтверждении и статус ресурсов

**Статус:** принято · **Дата:** 2026-10-16
**Источник идей:** разбор Snipek — [[Исследование-загнувшихся-проектов#Архитектура Snipek (разбор кода, 2026-10-16)]]
**Связано:** [[ADR-0007-исполнение-навыков]], [[ADR-0008-ядро-worker-очередь]], [[ADR-0012-диалог-контекст-выход-чтение]], [[Навыки]], [[Безопасность]], [[Архитектура]]

## Контекст

Мы разобрали архитектуру Snipek (голосовой ассистент под Sailfish на Snips, загнувшийся) и
вынесли три диалоговых решения, которых у нас **ещё нет**, и один UX-паттерн. У нас уже есть
автомат «хода» (`Idle → … → AwaitingConfirmation → …`) и `Command::Confirm`, но:

- **нет понятия «сессия хода»** — при многошаговом сценарии мы не знаем, *какому навыку* адресовать
  следующую реплику и когда чистить его состояние;
- **во время подтверждения автомат не сужает ввод** — теоретически может принять любую реплику;
- **выключенный навык** сейчас отсекается только в промпте (правило Q-5), но не в исполнении;
- **нет явного статуса ресурса** (LLM/STT), хотя модель грузится/выгружается по простою.

В Snipek это решено так: сессия (`sessionId`) + индекс «кто держит сессию»; `intent-filter`,
сужающий допустимые интенты на следующей реплике (при подтверждении — только `confirmation`);
подписка только на интенты включённых навыков; статус-модель внешнего ресурса
(`NotInstalled/Outdated/Stopped/Started`).

## Решение

1. **Сессия хода — первоклассная сущность.**
   - У активного хода есть `SessionId`. Пока ход **многошаговый** (подтверждение, уточнение слота),
     сессия остаётся «открытой».
   - В ядре — индекс **`session_id → skill_id`** (кто держит сессию). Следующая реплика в открытой
     сессии адресуется **тому же навыку**, а не маршрутизируется заново по интенту.
   - Навык может хранить **состояние сессии** (напр. курсор чтения списка). Оно очищается по
     завершении сессии и при сбросе («reset» — потеря связи/отмена), чтобы следующий ход начинался
     с чистого листа.
   - События: `Event::SessionStarted`, `Event::SessionEnded` (и внутренний сброс). Терминология —
     в `types/keys.rs`, без сырых строк.

2. **Сужение ввода при подтверждении (intent-filter).**
   - В состоянии `AwaitingConfirmation` ядро принимает ответ на подтверждение
     («да/нет»). Реплика, **не являющаяся ответом**, **не залипает** и не переспрашивает —
     сессия **выходит в новый навык** (см. [[ADR-0012-диалог-контекст-выход-чтение]]).
   - Подтверждение возможно **двумя путями**, оба ведут к одному решению:
     - **UI** — диалог → `Command::Confirm { approved }` (как сейчас в [[Безопасность]]);
     - **голос** — «да»/«нет»; пока ждём — другая команда не выполнится как «ответ да/нет»
       (нельзя случайно запустить другой навык, отвечая на вопрос).
   - Фильтр задаёт **ядро** (автомат), а не навык: это свойство стадии `AwaitingConfirmation`, а не
     логика конкретного навыка.

3. **Выключенный навык не исполняется, даже если его интент всё-таки пришёл.**
   - Усиление правила Q-5: помимо исключения из промпта, реестр/ядро **отвергает исполнение** навыка,
     чей `id` отключён в настройках. Список отключённых — единый источник и для промпта, и для
     исполнения (см. [[Навыки]]).
   - Пользователю **не молчим**, а явно сообщаем: **«такого навыка нет»** либо **«навык выключен»**.

4. **Статус-модель ресурса (LLM/STT).**
   - Тяжёлые локальные ресурсы имеют **явный статус**: `NotLoaded / Loading / Ready / Unloading /
     Error` (аналог `SnipsLocalAgent`). Статус виден движку и UI (страницы моделей), не «угадывается»
     по косвенным флагам.
   - Выгрузка по простою (`idle_unload_secs`) переводит `Ready → Unloading → NotLoaded`.

5. **Навык возвращает текст и никогда не трогает аудио.**
   - Подтверждение границы: результат навыка — данные (`Outcome`/текст ответа). Озвучкой занимается
     отдельный слой (`Speaking`, `piper`). Навык не вызывает TTS/микрофон.

6. **Дозапрос параметров (slot-filling) — вместо отказа.**
   - Если для запуска навыка **не хватает обязательных параметров**, ассистент **доспрашивает** их, а
     не отказывает. Манифест отдаёт свои `params` (имена/типы/обязательность) в **промпт**, чтобы
     модель знала: для запуска нужны **все** обязательные данные. При нехватке **модель формулирует
     уточняющий вопрос**.
   - Дозапрос ведётся **в той же сессии** (п.1): сессию держит навык, состояние — частично
     заполненный вызов. Если навык умеет **читать** кандидатов (`read`-метод), уточняющий вопрос
     конкретизируется списком. См. [[ADR-0012-диалог-контекст-выход-чтение]], [[Навыки]], [[Промпты]].

7. **Подтверждение ждём без таймаута** — пока пользователь не ответит (голосом или кнопкой UI).
   Ненужное ожидание всегда можно прервать: **повторное нажатие PTT** перебивает текущее, а
   **не-ответ** выводит в новый навык (п.2, [[ADR-0012-диалог-контекст-выход-чтение]]).

## Почему так

- Многошаговые сценарии (подтверждение, уточнение) становятся **детерминированными**: понятно, кто
  ведёт диалог и что принимается на следующем шаге.
- **Безопасность**: сужение ввода не даёт «ответом да/нет» случайно запустить другую команду.
- **Единый источник отключённых**: промпт и исполнение не расходятся.
- **Явный статус ресурса** убирает класс гонок/непонятных состояний при загрузке модели и улучшает UX
  (пользователь видит, что происходит).

## Последствия

+ Навыки получают чистое место для многошагового состояния и его уборки.
+ Подтверждение становится надёжным и для голоса, и для UI.
+ Выключённость навыка гарантирована на уровне ядра.
+ Статусы моделей/STT — предсказуемые, показуемые.
− Навык должен уметь обрабатывать «продолжение сессии» (не только первый интент).
− Нужны события и индекс `session_id → skill_id` в ядре (расширение [[ADR-0008-ядро-worker-очередь]]).
− Нужен механизм «выхода в новый навык» при не-ответе (см. [[ADR-0012-диалог-контекст-выход-чтение]]).

## Что НЕ перенимаем (анти-паттерны Snipek)

- **MQTT-брокер** как обязательный посредник — у нас одна очередь событий в одном процессе.
- **Внешнее проприетарное ядро** — корень смерти Snipek; наш «мозг» свой.
- **Один слот на интент** (`slotArr[0]`) — у нас полноценные `params`.
- **Пошаговое «прочитать следующий?»** как обязательная модель для списков — держим только там, где
  это оправдано (подтверждения), не как общий приём.

## Открытые вопросы

**Решено (2026-10-16, ответы Jack):**
- Подтверждение ждём **без таймаута** — пока не ответит.
- **Дозапрос данных — да**: при нехватке обязательных параметров **модель уточняет** (п.6).
- Выключенный/несуществующий навык → **сообщаем пользователю** (п.3).
- Единый термин — **«навык»** (не «команда»).
- **Микрофонный режим:** подтверждение/дозапрос — **повторное удержание PTT** (непрерывно открытый
  микрофон не держим; влияет на приватность/батарею). См. [[ADR-0012-диалог-контекст-выход-чтение]].
- **Перебить обработку/озвучку голосом — да**: это **повторное нажатие PTT** во время
  `Thinking`/`Speaking` (глушит текущее, начинает новую запись). См. [[ADR-0012-диалог-контекст-выход-чтение]].
- **Не-ответ в ожидании → выход в новый навык** (не «залипаем» и не переспрашиваем). См.
  [[ADR-0012-диалог-контекст-выход-чтение]].
- **Список при уточнении читает навык** (`read`-метод), а не спрашиваем вслепую. См.
  [[ADR-0012-диалог-контекст-выход-чтение]].
