# ADR-0007: Навыки — декларативное исполнение, один трейт `Skill`

**Статус:** принято · **Дата:** 2026-10-16
**Обновляет:** [[ADR-0004-формат-навыка]] · **Связано:** [[Навыки]], [[Безопасность]], [[Шаблоны-команд]]

## Контекст

Решали, как дать людям **добавлять и делиться** командами («навыками»), не превратив
приложение в площадку для распространения малвари. На устройстве (Sailfish 5.1.0.11)
по факту доступны: `busybox sh`/`ash` (это и `/bin/sh`, и `/bin/bash` — **без bashism'ов**),
`python3` 3.11.15 (с `python3-sqlite`), `perl`, `dbus-send`, `awk`/`sed`.
Нет: настоящего bash, lua/luajit, node, ruby, `sqlite3` CLI.

Ключевое наблюдение: **произвольный код нельзя валидировать — его можно только песочнить.**
Манифест описывает вход (`params`), но не описывает, что скрипт сделает с ним. Поэтому
«валидация навыка» и «язык исполнения» жёстко связаны: пока есть произвольный код, валидация —
фикция.

## Решение

1. **Никакого произвольного кода из разделяемых файлов.** `sh`/`python3`-скрипты из `.gskill`
   или по URL **не исполняем**. Это вектор для малвари (особенно при `Sandboxing=Disabled`),
   и их нельзя валидировать.
2. **Один трейт `Skill`** — единый интерфейс, с которым работает ядро:

   ```rust
   trait Skill {
       fn manifest(&self) -> Manifest;
       fn validate(&self, params: &Params) -> Result<()>;
       fn execute(&self, params: &Params, ctx: &Ctx) -> Result<Outcome>;
   }
   ```

3. **Две реализации, неразличимые для ядра:**
   - **`BuiltinSkill`** — на Rust, вкомпилирован (таймер, SMS, громкость, фонарь, открыть
     приложение…). Безопасно бесплатно, тестируется на хосте.
   - **`DeclarativeSkill`** — собирается **из манифеста** и выполняет один примитив:
     `dbus`-вызов / `open`-URI / **композицию** builtin'ов. Кода нет — только данные.
4. **«Пользовательские навыки» = декларативные привязки.** Добавляются файлом/папкой/URL
   **без правки кода приложения**. Одни и те же данные (`manifest`) питают:
   каталог интентов для промпта, валидацию и исполнение.
5. **Шаринг = рецепты/алиасы** («когда говорю X — сделай Y»), а не бандлы скриптов.

## Спектр исполнения (по возрастанию риска)

| Уровень | Механизм | Пользователю можно? |
|---|---|---|
| builtin | Rust, вкомпилирован, ревью в PR | контрибьютору |
| **декларативный** | `dbus` / `open` / композиция builtin — данные | **да, это и есть «пользовательские навыки»** |
| песочница | встроенный `rhai`/`lua` с урезанным capability-API | позже, продвинутым |
| sh / python3 процесс | ОС-команды из разделяемых файлов | **нет, никогда** |

Если позже понадобится «код» — только **встроенный интерпретатор с capability-API**
(мы решаем, какие функции вообще существуют: `get_time`, `read_sms`, `set_timer`, `speak`…;
ни файлов, ни процессов, ни сети сверх разрешённого). Принципиально иначе, чем `sh`: API
ограничивает не ОС, а мы.

## Почему декларатив лучше «просто shell»

D-Bus-метод описан данными — его эффект **виден и валидируем**: `{"dest":"…","method":"…"}`
можно показать в ревью-диалоге и ограничить. `sh script.sh` показать можно, а гарантировать —
нельзя. Плюс декларативный набор не размывает маленькую модель лишними интентами.

## Последствия

+ Безопасность по построению: нет исполнения чужого кода.
+ Валидация становится строгой и декларативной (язык больше не влияет).
+ Расширяемость без перекомпиляции: новый навык = данные.
+ Единая точка правды: `SkillRegistry` → промпт + валидация + исполнение.
− Сложнее выразить нестандартную логику (нужен builtin в Rust или позже песочница).
− Надо спроектировать capability-API песочницы (когда понадобится).

## Открытые вопросы

- Формат `.gskill`: **JSON inline** (читаемо, легко ревьюить) или архив (для крупных ассетов) —
  склоняемся к JSON-first.
- Коллизия `id` с builtin: полагаем — builtin `id` защищены, пользовательский переименовать.
- Набор примитивов `DeclarativeSkill` первого релиза (`dbus`, `open`, композиция).
