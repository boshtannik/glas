# План прототипа — интеграция ядра (walking skeleton)

> Состояние: **M0–M2 сделано (2026-10-17)**, дальше M3. Цель — соединить уже готовое ядро
> `glas-core` с приложением и получить **одну настоящую голосовую команду на устройстве**.
> Связано: [[План]], [[Архитектура]], [[ADR/0007-исполнение-навыков]],
> [[ADR/0008-ядро-worker-очередь]], [[ADR/0009-модельный-слой]], [[Возможности-ОС]].

## Зачем именно так

Дизайн связный, ядро реализовано и покрыто тестами, но `glas-core` **не подключён к
приложению** (`glas/Cargo.toml` его не тянет), а реальные навыки в ядре — фейковые. Все швы
(JSON-форма интента, доступ навыка к ОС, отмена, адаптер моста) вскроются только на сквозном
срезе. Поэтому сначала — **walking skeleton**: тонко, но end-to-end на устройстве.

## Definition of Done (скелет)

1. Приложение зависит от `glas-core`; диалог идёт через `Core` (автомат хода, `Command`/`Event`).
2. **Один настоящий навык** исполняется на устройстве и даёт **видимый эффект**.
3. Сквозной путь: удержание PTT → STT-текст → интент (candle) → навык → ответ + озвучка.
4. Собирается в RPM и ставится на телефон; проверено вручную.

|---|---|---|

## Ключевое открытие: таймер через CLI, а не через `add_event`

Сложную структуру `com.nokia.time` / `add_event` (`Maemo::Timed::event_io_t`) строить не нужно:
на устройстве есть CLI-клиент **`timedclient-qt5`** (и `timed`). Одна строка ставит настоящий
таймер:

```
timedclient-qt5 -b'TITLE=Стоп' -e'APPLICATION=glas;TITLE=Таймер;ticker=600'
→ event added, cookie is 58
```

- `ticker=<сек>` — сработать через N секунд; `-b` — кнопка (нужна, иначе событие отклоняется).
- Успех печатается в **stdout** (`event added, cookie is N`); cookie — это `id` таймера.
- **ГРАБЛЯ:** `APPLICATION` допускает только `[A-Za-z0-9_]+`. **Дефис запрещён** —
  `harbour-glas` отклоняется, поэтому `APPLICATION=glas`.
- **ГРАБЛЯ:** при ошибке `timedclient-qt5` печатает `event adding failed…` в **stderr** и
  выходит с кодом **0**. Поэтому полагаться на код возврата нельзя — парсим stdout на
  `cookie is N`; нет cookie → ошибка навыка.
- Отмена (для будущего `undo`): `timedclient-qt5 -c<cookie>`.

Это в духе `ADR-0010` (примитивы через ОС-утилиты), Qt внутри `timedclient-qt5` нас не касается.

## Архитектура среза

```
QML (ptt_start/ptt_stop/cancel)
  ▼
AppBridge (главный поток)
  ├─ ptt_start  → Recorder.start        → Command::CaptureStart → Core
  ├─ ptt_stop   → поток: whisper-cli ─┐
  ├─ llm_generate → поток: candle ────┤ результаты в poll()
  └─ tts_speak  → поток: piper        │
        poll()  ◀─────────────────────┘
          │  (транскрипт / вывод LLM / аудио)
          ▼
        Core.handle(Command)  →  Vec<Event>
          ▼
   Event → свойства моста (answer/status/tts_file) + QML
```

- `Core` — синхронный, владеется мостом; вызовы из `poll()` (главный поток).
- Навыки видят ОС через `Ctx { system: &dyn System }` (сейчас `Ctx` пуст — расширить).
- `Event::Reply` → `answer` + автоозвучка; `NeedsConfirmation` → диалог; `Error` → поверхность.

## Что НЕ входит в скелет (осознанно)

- `DeclarativeSkill`, `.gskill`, шэринг, журнал/undo (SQLite), статус-модель ресурса.
- Отдельный worker-поток с единой очередью (пока `poll()` на главном потоке).
- Второй и последующие реальные навыки (кроме заявленного).
- Виртуализация/смоук-тесты на хосте для Qt-обвязки (Qt не собирается на хосте) — только ручной смоук.

## Риски

- **D1 (JSON-форма)** — несущая балка; без решения интент нестабилен. Митигация: строгий парсер +
  retry, отдельные тесты парсинга (уже есть базовый `intent::parse`).
- **Qt-крейт не тестируется на хосте** → логика держится в `glas-core`/`glas-system` (host),
  в мосте — минимум «клея».
- **Медленный цикл сборки/деплоя** (Docker/sb2) — мелкие итерации, проверки на хосте где возможно.
